# ADR-0031: 認証手段を足す操作の前の再認証を、直近のログインの時間窓で行う

## Status

Accepted (2026-11-23)。判断主体は maintainer。仕様の正本は taimei-code/taimei-auth#481、実装は #481 のサブ issue で行う。[ADR-0013](./0013-mfa-totp-challenge.md) §5 の「再認証を置かない」を改め、[ADR-0029](./0029-passkey-self-owned-webauthn.md) の Consequences にある「パスキーの登録の前の **TOTP** の確認」を置き換える。

## Context

今は **session** があれば、MFA の登録と有効化、パスキーの登録ができる。session を奪った攻撃者は、自分のパスキーを足せば、奪った session が切れた後も入れる。自分の認証アプリで MFA を有効にすれば、本人を締め出せる (ADR-0013 §5)。MFA を有効にした user のパスキーの登録だけは、登録の前に **TOTP** のコードを確かめている (ADR-0029)。

ADR-0013 §5 は登録と有効化の直前に再認証を置かないと決めた。理由は、ログインの動線が二重になるコストが常にかかることだった。再評価の契機には「step-up を要する操作が他にも増えたとき」を挙げ、その時は共通の仕組みとして設計するとしていた。パスキーの登録が加わり、この契機に当たった。

再認証の手段は MFA を有効にしていない user、パスキーを持たない user、GitHub OAuth でログインする user も通れる必要がある。

## Decision

- 手段は「直近のログインの時間窓」とする。**session** の発行から 10 分を過ぎていたら、認証手段を足す操作を既知の失敗で拒否し、ログインし直させる。MFA を有効にした user の **session** は **MFA チャレンジ** を通った後に発行されるので、第二要素を確かめた時刻が基準になる。10 分は **MFA チャレンジ** の有効期間と同じで、ログインし直してから 1 つの操作を終えるのに足りる長さである
- 判定は自前で行い、better-auth の `freshAge` は 0 のままにする。`freshAge` を 10 分にすると、セッションの一覧など better-auth のほかの endpoint も、発行から 10 分を過ぎた **session** を拒むため
- ログインし直しには、今あるログインの手段 (**Magic Link**、GitHub OAuth、パスキー) と **MFA チャレンジ** をそのまま使う。再認証専用の手段、token、状態は持たない。そのため、ADR-0013 §5 が退けた「ログインの動線が二重になるコスト」は、元の操作へ戻す分だけになる
- 対象は MFA の登録と有効化、パスキーの登録とし、すべての user に求める。MFA の無効化とパスキーの削除は対象にしない
- パスキーの登録の前の **TOTP** の確認は外す。MFA が有効な user がログインし直すと、**MFA チャレンジ** かパスキーのログインを通るので、確認が重複するため
- GitHub の連携を後から足す経路 (better-auth の link-social) は、画面から呼ばれていないので塞ぐ。GitHub でのログイン時に同じメールの user へ行われる暗黙の連携は、対象にしない。session を持った攻撃者の操作ではなく、被害者のメールを GitHub 側で確認済みのアカウントが要るため

## Considered Options

| 順位 | 案 | 選ばなかった理由 |
|---|---|---|
| 1 | 直近のログインの時間窓 | (採用) |
| 2 | Magic Link を操作の直前に送り直す | 再認証専用の token と TTL の状態、メールのテンプレートが増え、毎回メールを往復する |
| 3 | TOTP、パスキー、Magic Link から選ぶ | 手段ごとに分岐が増え、状態も増える |
| 4 | TOTP かパスキーだけ | MFA を有効にしておらず、パスキーも持たない user が通れない |

## Consequences

- 受容するリスク: 発行から 10 分以内の **session** を奪われた場合は防げない。MFA を有効にした user のパスキーの登録も同じで、今は登録の前の **TOTP** の確認が防いでいる分を受容する。GitHub OAuth の user は、GitHub 側でログイン済みなら操作なしでログインし直せる
- 受容するリスク: **kill switch** で **MFA チャレンジ** を止めている間は、MFA を有効にした user も一次認証だけでログインし直せる。その間に足したパスキーは switch を戻した後も残り、そのパスキーでは **MFA チャレンジ** を通らずにログインできる。パスキーの登録は本人に通知メールが届くので、switch を戻した後に、止めていた間に登録されたパスキーを確かめる
- MFA の登録の後、10 分を過ぎてから有効化しようとすると拒否され、ログインし直すことになる。**登録済み未有効** の間は同じ登録内容を返すので、認証アプリの登録はやり直さずに済む
- 画面は、再認証が要るという既知の失敗を受けたら、利用者をログインし直しへ導き、済んだ後に元の操作へ戻す。導き方は #481 のサブ issue で決める
